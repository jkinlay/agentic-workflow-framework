Purpose and boundaries

02 / 15

The delivery control problem

Unstructured AI work

  • Scope, ownership and evidence drift apart
  • Review readiness can be confused with approval
  • Unknown external outcomes invite unsafe retry

AWF makes decisions observable

  • Bounded tickets, named roles and protected records
  • Candidate-bound validation and independent review
  • Explicit gates for host actions and human authority
No autonomous agent launch No automatic merge No Jira state mirroring
AWF coordinates and records controlled work. Hosts and authorised humans retain external authority. Source: AWF 1.8.9 Manual §§2, 4

1.5 minutes

Frame the value as control and observability. Do not claim that AWF independently launches agents, changes repositories, merges code or mirrors Jira states. Those boundaries are deliberate.

Source: AWF 1.8.9 Manual §§2, 4.

2.5 minutes

Walk left to right. A critic approval and final gate do not authorise a merge. The owner authorisation binds the exact candidate, expires and is consumed once. Changes requested loop back through bounded amendment and fresh review. A merge uncertainty becomes MERGE_UNKNOWN until remote state is reconciled; only then can an optional post-merge Jira boundary be considered. Publisher, worker and host/operator are distinct roles, not a universal requirement for independent actors; apply only the independence and credential separations required by the selected mode.

Source: AWF 1.8.9 Manual §§3, 12.

Setup for a new project

07 / 15

New-project adoption follows a controlled sequence

01Verified source and cacheUse the independently pinned distribution.
02Isolated adoption branchEstablish exclusive worktree ownership.
03Locked Python runtimeCreate it before either bootstrap call, outside the worktree.
04Bootstrap dry runReview proposed derivation and residue with that runtime.
05Backed-up bootstrapRun non-dry installation with same-filesystem backup handling.
06Installed checksVerify installation, configuration, status and operating choices.
07Draft owner-review PRRecord evidence and await accepted governance change.
Both bootstrap calls use the locked runtime. If bootstrap returns INSTALLED_UNCONFIGURED, stop, remedy and rerun bootstrap or recovery; later checks do not rewrite that result. Source: AWF 1.8.9 Manual §§5, 7

2 minutes

The ordering matters. Lock the runtime before the dry run, then use that same runtime for both bootstrap calls. The non-dry-run bootstrap runs its own verification and configuration checks. If it returns INSTALLED_UNCONFIGURED, stop, remedy and rerun bootstrap or recovery; later standalone checks do not rewrite the bootstrap result. The output is a draft adoption PR, not a direct change to the default branch.

Source: AWF 1.8.9 Manual §§5, 7.

Routes, budgets and recovery

10 / 15

Reserve before launch. Preserve uncertainty.

01SuggestEvaluate an allowed route with no side effect.
02ReserveRecord bounded run and budget in protected durable state.
03Host launchLaunch only through an actually capable host.
04SettleRecord observed model, usage and outcome against the reservation.
Unsupported routeReturn unavailable. Do not silently downgrade.
Unknown usage or outcomeKeep the charge and the unknown. Unknown is not zero.
Mismatch or overrunQuarantine the project and prevent positive evidence.
ReconciliationOptional and disabled by default. It needs named authorised operators and protected host controls, records assertions and never becomes positive evidence.
Incident ceilingDefault two reconciled incidents per ticket across roles, phases and policy. A third blocks new admission; only a trusted host can raise the ceiling with one-time, time-bounded approval evidence.
Recovery is evidence-led and fail-closed. Blind retry is not a recovery path. Source: AWF 1.8.9 Manual §§11, 17

2 minutes

Explain why reservation precedes launch. It makes route and budget controls durable. Do not present reconciliation as a routine loop: it is disabled by default, separately controlled and cannot turn an uncertain result into positive evidence. The default reconciled-incident ceiling is two per ticket across roles, phases and policy. A third blocks new admission. Only a trusted host may raise that ceiling using authentic, one-time approval evidence that expires within 24 hours of the original approval.

Source: AWF 1.8.9 Manual §§11, 17.

Observed Jira delivery proxy

21.1× Illustrative planning-capacity ratio only. Jira measures Fixed work items, while the assumption measures merged PRs. This is not a measured productivity uplift or a causal AWF claim.
Jira proxy, not merge count: QA JQL with resolution = Fixed, 1 Jan–30 Jun 2026. Accessible Jira fields did not expose a reliable merged-PR count. Planning assumption: Jonathan Kinlay, 18 Sep 2026

1.5 minutes

Keep the units separate. The observed Jira proxy is 423 QA work items resolved Fixed from 1 January through 30 June 2026, divided by 124 England and Wales business days: 3.41 Fixed work items per business day. If the same eight people supported that project throughout, the implied simple per-person rate is 0.43 Fixed work items per business day; it is not an observed FTE measurement. Jira's accessible fields did not permit a reliable merged-PR state count, so do not describe 3.41 as merged PRs. Although sampled work items link to GitLab merge requests, the exposed Jira data does not provide a defensible merge-state aggregate.

The 72 is a planning assumption supplied by Jonathan Kinlay on 18 September 2026: 9 merged PRs per analyst per project day times eight people. It means aggregate team capacity if each analyst has one active project; it must be allocated across projects and is not multiplied again by project count. 72 divided by 3.41 gives 21.1, but that compares non-equivalent units. It is neither an observed AWF result nor an AWF productivity claim.

For a fair pilot comparison, predeclare confirmed merged GitLab PRs linked to QA keys per FTE-week and pair them with aligned ticket outcome, lead time, rework or escaped defects, CI and independent-review quality, human effort, model usage and cost, failure or recovery record, and stop or expand thresholds. Compare a matched repository and work-type baseline before inferring a causal effect.

Observed source: Jira project QA query project = QA AND resolution = Fixed AND resolutiondate >= "2026-01-01" AND resolutiondate < "2026-07-01", queried 18 September 2026. Planning assumption source: Jonathan Kinlay, 18 September 2026.
