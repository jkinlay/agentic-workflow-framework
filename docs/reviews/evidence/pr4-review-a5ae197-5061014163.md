## Inline findings

### tools/canary/volume_bars.py:45

**[critical] AC2 not implemented: trailing partial bar is silently dropped (data loss)** (blocking)

`volume_bars` never emits the residual bucket after the loop ends. Any prints accumulated below `threshold` at end of stream are discarded, so prints are lost — directly violating AC2 ("The final partial bar is emitted with partial set to true so that no prints are lost"). The `partial` field and the `partial` parameter of `_make_bar` are therefore dead code (always False). Fix: after the `for` loop, add `if bucket: yield _make_bar(bucket, partial=True)`. Add a test with e.g. ticks summing to 150 against threshold=100 asserting a second bar with volume 50 and partial=True.

_AWF finding F1, phase blind_

### tools/canary/volume_bars.py:51

**[critical] AC3 violated: vwap is an unweighted mean of prices, not volume-weighted** (blocking)

`_make_bar` computes `vwap = sum(prices) / len(prices)` — a simple arithmetic mean of tick prices, ignoring size entirely. AC3 requires `sum(price * size) / sum(size)`. For the ticks in `test_bars_close_at_threshold` (10.0@60, 11.0@40) the correct vwap is 10.4 but the code returns 10.5. This is a numerically wrong market-data statistic that would silently propagate into any downstream research or execution logic. Fix: `vwap = sum(t.price * t.size for t in bucket) / volume` (guard volume > 0).

_AWF finding F2, phase blind_

### tools/canary/test_volume_bars.py:25

**[high] AC5 gap: no test asserts vwap, and no test covers the partial-bar path** (blocking)

The test module has zero assertions on `bar.vwap` (AC3) and zero coverage of a trailing under-threshold bucket (AC2). This is exactly why both defects shipped undetected. `test_complete_bars_are_not_partial` only asserts the negative case, so the `partial=True` branch is never exercised. Add: (1) a vwap test with unequal sizes, e.g. Tick(1,10.0,60), Tick(2,11.0,40) at threshold=100 asserting vwap == 10.4; (2) a partial test asserting the residual bar exists with partial=True and correct volume; (3) a negative test for threshold < 0 (AC4 only tests 0).

### tools/canary/volume_bars.py:39

**[medium] No validation of tick size/price; zero or negative sizes can cause infinite-size buckets or ZeroDivisionError**

`volume_bars` accepts any `Tick`. A tick with size <= 0 (bad print, cancel/correction) contributes nothing or negatively to `accumulated`, so a bucket may never reach threshold; once vwap is correctly volume-weighted, a bucket whose sizes sum to 0 will raise ZeroDivisionError. There is no negative test for malformed input. Fix: reject or explicitly document handling of size <= 0 and non-monotonic timestamps, and add tests.

### tools/canary/volume_bars.py:43

This is a defensible design choice for volume bars, but it is neither documented nor tested, and downstream consumers assuming uniform bar volume would be silently wrong. Fix: document the behaviour in the module docstring and add a test pinning it.
