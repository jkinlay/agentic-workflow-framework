Act 3: control and limits

13 / 14

What you control, what it will not do

OPERATING_CONFIG.yaml

Change by direct instruction Streams and approved routes for subsequent dispatch. Running reservations retain their original operating hash.

.agentic/PROJECT_CONFIG.yaml

Change through a reviewed PR Ceilings, allowlists, review floors, budgets, merge policy and recovery controls remain protected.
Owner takeaway

You control operating choices

A direct request that exceeds a protected ceiling or weakens review is refused rather than silently applied.

Six non-goals
  • Does not launch agents or attest that a model ran.
  • Does not merge code.
  • Does not create tickets, update Epics or mirror workflow states into Jira.
  • Does not treat a review approval as merge authority.
  • Does not retry an uncertain merge, Jira write or provider outcome.
  • Does not enable the external reviewer or scheduled loop because a project is ACTIVE.
Protected governance changes need a reviewed PR. Optional live components have their own qualification.Source: .agentic/SPECIFICATION.md · Authority and modes

Keep the authority boundary plain. Worktrees are not isolation. Candidate content cannot grant permission. Secrets, trusted state and routing ledgers remain outside workers. The optional scheduled review loop and external review adapter each require separate qualification. Unknown effects require reconciliation before any retry.

Appendix A

Evidence states

Adoption proof and candidate-bound evidence

StateWhat it provesWhat it does not prove
UNVERIFIEDNo current accepted adoption proof.Nothing about safe installation or live readiness.
INSTALLEDManaged bytes match installation receipt.Accepted policy, release provenance or live authority.
CONFIGUREDInstalled verification and configuration validation accept current state.Independent release trust or enabled live adapters.
ACTIVEIndependent release trust, observed adoption merge and fresh accepted raw bytes.Agent launch, merge, Jira writer or adapter qualification.

Evidence invalidation

  • Candidate changesHead, base, target, merge method, requirements or policy change invalidates affected review, gate or authorisation evidence.
  • Blocking findingsOpen or disputed BLOCKER and MAJOR findings prevent readiness. Resolution remains linked to evidence and fresh independent review.
  • Unknown effectsMERGE_UNKNOWN and uncertain Jira outcomes require authoritative reconciliation before any retry.
  • Durable evidenceKeep requirements/policy hashes, PR identity, test/CI provenance, reviews, gate, authorisation, routing and reconciliation outside worker worktrees.

Optional components

Optional adapters, recovery and command reference

Optional components

  • Scheduled review loopOne explicitly enrolled existing GitHub.com PR. It can run critic, bounded amendment, fresh critic and current-head CI. It never creates the first PR, merges or writes Jira.
  • External review adapterSeparate provider, secrets, credential scope and qualification requirements. Native/scheduled evidence does not qualify it.
  • Qualified hostObserved rules, CI, trusted merge owners, actual resource limits, credential boundaries and recovery procedures remain project-specific evidence.
  • RecoveryPause, preserve run evidence and reconcile exact state before resume. Do not reset accounting or create a second ledger.
