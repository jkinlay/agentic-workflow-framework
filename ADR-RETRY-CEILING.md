# Protected retry ceilings and default policy identity

Ordinary configuration previously determined the reconciliation retry cap on every admission. Editing it could silently expand retries, although prose required human direction. Adding an explicit default also changed evidence identity despite identical effective settings.

The host-controlled ledger derives each project's ceiling from append-only events. Admission seeds it conservatively at the lower of 2 and the reviewed configuration, audits reductions and rejects higher configured limits. Each event records project, revision, prior/new limit, timestamp and provenance. A trusted-host-only operation increases it using an exact proposed-policy binding, expected prior ceiling/revision, operation ID, original approval time, expiry and human authorization/evidence references. Transactions serialize changes. Revision comparison rejects stale approvals even when the numeric ceiling returns to an earlier value. Replay cannot undo a later reduction. Safe closure never depends on admission capacity.

A validated reduction is an observation independent of whether work can run. One `BEGIN IMMEDIATE` write lock covers observation and admission; a savepoint rolls back admission work while preserving the observation on recoverable admission errors, including outstanding work, quarantine, budget exhaustion and missing required cost. The helper commits before re-raising the error. Savepoint/commit failures remain errors; process termination does not guarantee that an uncommitted observation survived. Reductions carry `attempted_run_id` and `request_sha256`, fingerprinting project, effective policy hash, complete caller request and capabilities. Successful admission uses that same UUID in `model_runs`; a denied UUID is only an attempt and creates no reservation or charge. Results and library exceptions expose the attempt binding. No approval can interleave between observation and admission under the write lock.

This is enforcement against ordinary configuration edits, not a new authentication service. The host must exclude workers from direct ledger writes and the privileged operation, and authenticate human direction before calling it. Python references and operator IDs are assertions. No ordinary routing CLI command exposes the increase operation.

New policy fingerprints include effective reconciliation defaults. Evidence admits only legacy hashes of the exact equivalent omitted-default representations. Stored rows and provenance hashes remain untouched and visible. Substantive policy differences remain separate. Representation compatibility does not establish past host behavior, causal model quality or live qualification.

Opening an older ledger transactionally imports each current ceiling once and seals the legacy table against inserts, updates and deletes. Migration preserves existing authorization records and marks unknown historical reduction provenance explicitly. A separate consumption index imports each historical authorization/evidence identity once, preserving historical duplicate grants and their original rows. Consumption is shared across both reference fields and every project in the same canonical database. Events, authorizations and consumption entries reject updates, deletes and replacement/upsert writes. These guards do not authenticate a database owner who can insert records or drop triggers. Protect the database and API; a new/copied ledger does not provide cross-database replay protection.

New grants require aware timestamps with `approved_at <= now < expires_at <= approved_at + 24 hours`. The host supplies the actual original approval time, not the submission time, and retains its immutable source evidence. Time is checked under the write lock and expiry rechecked before consumption. The helper cannot authenticate human direction, source time or a reference's provenance. Both references must be stable canonical host identities: NFC normalization preserves case; new references reject surrounding whitespace and control characters. Arbitrary URL/source aliases are not resolved. The same identity can fill both fields once; any later use in either field is rejected even with a fresh operation ID, revision, policy or project.

Exact recorded requests return their historical result after expiry without changing state, including v1.8.1/v1.8.2 shapes lacking new fields. New old-shaped requests are rejected. Applied ceilings remain durable until reduced. Pause admissions while staging the proposed policy, recording approval and installing that policy; an old-policy admission can lower a new ceiling. See [migration](MIGRATION-v1.8.2-to-v1.8.3.md). Restoring an older router requires host review and preserved state: old code can bypass new logic or conflict with sealed tables.
