# Adopt the 1.8.3 patch

Use the existing-project adoption guide for any repository, including partially completed projects. Verify independently supplied source/archive pins. Record and back up the accepted installation, actual project configuration, Jira mappings, active work and canonical external state before preparing a reviewed adoption PR. Preserve historical evidence and approval identities. A cross-version adoption is a reviewed backed-up install; same-version `--mode upgrade` is not a migration across releases. Installing the portable skill updates discovery only.

## Retry authority

Pause admissions and back up the trusted routing database consistently. Opening it with the new router indexes references already consumed by historical retry-limit grants. It preserves existing grants and their exact replay results, including historical duplicated references; it does not invent approval times or retroactively invalidate prior results. Keep every host for this project on the same protected canonical ledger and approved runtime.

New grant observations require `approved_at` in addition to the previous revision/expiry fields. The trusted host must authenticate the actual source approval, its time, exact project/policy/limit/revision binding and stable approval-specific evidence identity before calling `authorize_retry_limit`. Submit the source time rather than the current call time. First use must be after approval and before expiry, with expiry no more than 24 hours after approval. The host must reject revoked or edited approvals; the library cannot establish external source authenticity or detect every alias for a human message.

Both `authorization_ref` and `evidence_ref` are single-use in the canonical database. Supporting evidence must identify this approval's immutable receipt, not a general incident document reused for multiple grants. NFC-normalized identities remain case-sensitive; the host supplies stable canonical identifiers. A changed operation ID, policy, project or expiry cannot reuse an indexed reference. Separate databases cannot provide global replay protection. Exact already-recorded requests return history without restoring a later-reduced ceiling.

Stage the proposed policy while admissions are paused, obtain fresh approval, record the increase, install that identical policy and resume. Old unrecorded grant shapes now reject. New historical lookup/replay does not create approval authority. Rollback must preserve consumption records, reduction events, reservations, charges and later approvals; an older router can bypass new rules. Do not reset the ledger to recover capacity.

Validated configuration reductions persist even if later admission rejects outstanding work, a quarantine or an exhausted/missing budget. The reduction is associated with an attempted run UUID and context fingerprint. A denied attempt is not a dispatched or charged run. Check the audit and rejection's attempt metadata before proposing an increase back to the former ceiling. Invalid configuration and interrupted uncommitted transactions do not establish a durable observation.
