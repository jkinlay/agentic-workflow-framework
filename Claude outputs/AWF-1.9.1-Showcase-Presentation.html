AI agents write the code. You sign the merge.

Why it matters

You already have PR review, CI and branch protection. AWF adds five things.

AdditionWhat it doesWhy a normal repo doesn't give you this
1 · Ticket contractAcceptance criteria, allowed files, forbidden changes and risk tier are fixed before the agent starts.An issue is free text. The agent can quietly widen scope, and nothing checks it against the original ask.
2 · Independent criticA separate, read-only agent reviews the exact commit, and may only block on an acceptance criterion or a mandatory boundary.Human reviewers skim large agent diffs. Self-review by the same agent context is worthless.
3 · Budget before workModel, effort and spend are reserved before a run and settled after it. Unknown cost is never treated as zero.Agent spend is usually discovered on the invoice.
4 · Approval that works onceYour merge approval is bound to one commit, expires, and cannot be reused.A green review on an old commit looks the same as one on the new commit.
5 · No blind retriesIf a merge or Jira update has an unknown outcome, AWF stops and reconciles instead of trying again.Agents retry by default, which is how you get double writes.
It does not replace GitHub, CI, Jira or your judgement. It sits between the agent and them.ARCHITECTURE.md · SPECIFICATION.md

"The fair comparison isn't AWF versus a chat window. It's AWF versus what a well-run team already has: pull requests, CI and branch protection. AWF keeps all of that and adds five things."

"First, the ticket becomes a contract before work starts. Second, a separate critic reviews the exact commit and can only block on something in that contract or a hard boundary, so it can't nitpick forever. Third, spend is reserved up front. Fourth, my approval is tied to one commit and works once. Fifth, when something has an unknown outcome, it stops rather than retrying."

"What it isn't: it's not a new tracker, not a CI system, and it doesn't take the merge decision away from you."

How it works

Codex runs the agents. AWF sets the rules and keeps the record. You hold the merge.

Worker and critic never share a context. Agents cannot write to the ledger. Only the controller writes to Jira.ARCHITECTURE.md · SPECIFICATION.md

"This is the whole machine on one slide. Codex is the engine: it runs the agents. AWF is the rulebook and the record: it defines what a ticket contract is, what a review must contain, and what evidence the gate needs."

"A ticket becomes a contract. The controller dispatches a worker into its own branch. The worker opens a draft PR. CI runs on that exact commit, and a separate critic reviews that same commit in its own context; it can read, not write. The final gate checks that everything is still current. Then it comes to me."

"Underneath is a ledger that the agents can't touch: budgets, reviews, approvals. And only the controller talks to Jira, so you don't get five agents fighting over ticket status."

An agent could forge your sign-off

Appendix D · Boundaries

D

What AWF will not do

  • Launch agents or attest that a model ran; the host (Codex) does that.
  • Merge code, release, publish, or promote research to production.
  • Treat a green review as permission to merge.
  • Retry a merge, Jira write or provider call whose outcome is unknown.
  • Create tickets, update Epics or invent issue keys.
  • Let an agent loosen budgets, ceilings, allowed models or review floors.
  • Switch on the scheduled review loop or external reviewer just because a project is ACTIVE.
  • Keep secrets, ledgers or trusted state inside an agent's worktree.
Optional components (scheduled review loop, external reviewer, Jira writer) each need their own qualification..agentic/SPECIFICATION.md · ARCHITECTURE.md
